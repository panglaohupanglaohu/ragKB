## 一、系统总目标（对齐基准）

> 构建智能体群及相应的智能体，让智能体在议事广场进行讨论，根据讨论出的执行计划及讨论文案萃取相应的技能；技能可以演进并且在沙箱中验证；通过验证的技能按照**特有技能、通用技能、储备技能**分类。在数字孪生模块，针对智能体之间的协作结合业务场景进行试错及演进推导，做**智能体协作尝试**及**技能路由尝试**，给出评分；通过**正向棘轮**驱动整体系统演进；针对各个智能体团队及服务评估 **token 消耗**，达到整体智能体组**可持续化的优良配置**。

把总目标拆成七个能力环节，逐一对照现状：

| # | 环节 | 承载模块 | 现状 | 缺口等级 |
|---|------|---------|------|---------|
| 1 | 议事广场讨论 → 执行计划 | `plaza_engine`(51k行级) / `plaza_routes` / `plaza_consensus` | ✅ 讨论、共识、plan_revision 完整 | 低 |
| 2 | 讨论文案 → 技能萃取 | `skill_extractor` / `extraction_pipeline` / `extraction_routes` | ✅ 管线存在，⚠️ 与 plaza 共识非自动联动（需手工发起） | **中** |
| 3 | 技能演进 + 沙箱验证 | `skill_evolver` / `evolution/` / `skill_verifier` / v4 `evolution_bridge` | ✅ v4 已打通"演练数据→进化→A/B→门禁写回" | 低（v4 完成） |
| 4 | 技能三类分类 | `skill_library`（visibility: private/public/builtin + lifecycle 六阶段） | ❌ 没有"特有/通用/储备"三类语义，缺分类规则与自动归类 | **高** |
| 5 | 孪生协作试错 + 技能路由尝试 + 评分 | v4 场景演练（协作✅ 评分✅）/ `skill_router`（路由独立存在） | ⚠️ 技能路由策略未进入孪生试炼做 A/B | **中** |
| 6 | 正向棘轮驱动系统演进 | `twin_loop` 演化模式棘轮（会话内）/ `datacenter_api` 棘轮演示 | ❌ 无**系统级**棘轮账本：跨试炼、跨团队的"只进不退"没有统一记录与门禁 | **高** |
| 7 | Token 消耗评估 → 可持续配置 | `cost_aggregator` / `cost_policy` / `ci_cost_gate` / `token_factory` | ⚠️ 成本采集与策略齐备，但**没有"评分×成本"的效率视角**与配置优化建议 | **高** |

**结论：链路上游（1-3）与孪生演练（5 的协作半边）已经成型；当前全局瓶颈是 4、6、7 三个"收口"环节——技能分类法缺失、系统级棘轮缺失、可持续性评估缺失。** 它们决定整个闭环的产出能否沉淀、能否只进不退、能否长期付得起。

## 三、核心设计

### 3.1 G-2 技能三类分类法（SkillClassifier，最高优先级）

在既有 `visibility`（private/public/builtin）与 `lifecycle_stage`（draft→solidified）之上引入正交的 `classification` 维度：

| 分类 | 语义 | 判定规则（数据驱动，全部来自演练/使用证据） |
|------|------|------|
| **特有技能 exclusive** | 某团队的竞争力技能，不外溢 | 单团队使用占比 ≥80% 且 effectiveness ≥0.6 且演练成功率达 rubric 期望 |
| **通用技能 general** | 跨团队/跨场景验证有效，进公共池 | ≥2 团队采用（adopted_by）或 ≥2 场景类目演练达标，且通过发布门禁 |
| **储备技能 reserve** | 暂不达标但有潜力：新萃取、低使用、进化中、降级回收 | 新建默认；或 effectiveness <0.4；或 lifecycle=degraded；或 90 天未使用 |

要点：分类不是人工标签而是**定期重算的函数** `classify(skill, usage_evidence, trial_evidence) -> classification + reasons`；分类变化产生事件（reserve→general 是"毕业"，general→reserve 是"降级回收"），降级自动建议进入 v4 进化闭环。储备池是进化候选的主要来源——这把"技能分类"和"技能进化"焊在一起。

### 3.2 G-4 全局正向棘轮账本（RatchetLedger）

现有棘轮只在单次演化会话内生效（`twin_loop._run_evolutionary` 的 gen 比较）。全局账本把"只进不退"提升到系统级：

- **账本条目**：`(metric_key, generation, value, evidence, timestamp)`，metric_key 形如 `scenario_best:{scenario_id}:{team_id}`、`skill_effectiveness:{skill_id}`、`cost_efficiency:{team_id}`。
- **推进规则**：`advance(metric_key, new_value, evidence)` — 仅当 `new_value >= current + min_delta`（默认 min_delta=0）才推进 generation 并记账；否则返回 `{advanced: False, reason}`。容忍参数 `tolerance` 允许有界波动（如 cost 类指标 2%）。
- **接线点**：trial evaluate 完成 → 尝试推进 `scenario_best`；evolution_bridge promote → 尝试推进 `skill_effectiveness`，**推进失败时阻断写回**（棘轮成为晋升门禁的一部分）；sustainability 评估 → 推进 `cost_efficiency`。
- **持久化**：`storage/ratchet/ledger.json`，原子写 + 备份，对齐 trial_store 模式。
- **可视化**：账本曲线即"系统演进史"，供 system-evolution.html 消费。

### 3.3 G-5 Token 可持续性评估器（SustainabilityEvaluator）

把 `cost_aggregator`（消耗侧）与 trial 评分（产出侧）连起来：

- **核心指标**：`token_efficiency = total_score / (tokens_consumed / 1000)`（团队×场景粒度）；`sustainability_score = w1*efficiency_norm + w2*trend + w3*budget_headroom`。
- **配置建议引擎**（规则版，先不上 LLM）：效率低 + 模型贵 → 建议降档模型；团队人数 > 场景 roles 需求 → 建议缩编/转储备；某 skill 调用多但成功率低 → 建议路由到高熟练度 agent 或触发进化；预算余量 <20% → 建议降低演练频率/步数上限。
- **数据接口容错**：cost_aggregator 不可用时接受手工/估算输入（v4 evolution_bridge 的 cost_tokens 即估算来源之一），保证评估器离线可用。
- **闭环**：评估输出作为议事广场的下一轮议题素材（"本周期 xx 团队 token 效率下降 30%，请讨论调整方案"）。

### 3.4 G-3 技能路由试炼（路由策略进孪生）

`skill_router` 已有 affinity/feedback 机制但独立运行。改造：试炼创建时可指定 `routing_strategy`（proficiency_first / affinity_first / round_robin / cost_aware），twin 决策时按策略选 skill 执行人；不同策略 fork 对照分支跑同场景，评分对比即"技能路由尝试"。路由试炼结果通过 `submit_feedback` 写回 router 的 affinity，形成第二条进化回路（agent×skill 配对进化，与 v4 的 instructions 进化互补）。

### 3.5 G-1 议事广场→萃取联动

plaza 讨论达成共识（consensus/plan finalized）时发出 `PLAN_FINALIZED` 事件 → 自动创建 extraction pipeline 任务（来源标记 `plaza:{discussion_id}`）→ 萃取出的技能默认入**储备池** → 走验证/分类流程。人工确认开关保留（默认开启自动、可在 settings 关闭）。

## 四、分阶段路线

| 阶段 | 内容 | 性质 |
|------|------|------|
| **P0**（本轮实施） | G-2 SkillClassifier + G-4 RatchetLedger + G-5 SustainabilityEvaluator 三个收口件（模型+引擎+API+测试），并接线到 v4 evaluate/promote | 新增模块为主，低侵入 |
| **P1** | G-3 路由试炼（twin_loop 决策策略化 + 对照分支）；G-1 plaza→萃取钩子；三收口件接入真实 cost_aggregator 数据 | 改造既有模块 |
| **P2** | 前端：system-evolution.html 棘轮账本曲线、cost-dashboard 效率视角、技能库三池视图；nightly 定时分类重算与可持续报告 | 可视化与自动化 |

P0 三件套互相独立、均可纯逻辑测试，是总目标 4/6/7 三个高缺口的直接补位。

## 五、风险与边界

- **分类抖动**：使用数据稀疏时分类频繁翻转。缓解：毕业需连续 2 个评估周期达标；降级有 1 周期宽限。
- **棘轮僵化**：min_delta 过严会卡死所有晋升。缓解：默认 min_delta=0（持平可过）、cost 类指标设 tolerance；账本支持人工 `force_reset(metric, reason)` 留痕重置。
- **成本数据缺失**：opencost/cost_aggregator 在部分环境不可用。缓解：评估器接受估算输入并标注 `data_quality: estimated`。
- **不做**：本轮不改 plaza_engine 内核、不上 RL、不做多目标帕累托优化（棘轮单指标向量已够用）。
